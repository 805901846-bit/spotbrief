# PatchBrief 端到端评测集设计规格

## 1. 目标

构建一套由 Codex 可直接运行、评分和解释的 PatchBrief 端到端评测集，回答一个核心问题：与只向 AI 编码助手提供普通自然语言需求相比，PatchBrief 生成的结构化任务书是否能提高前端修改的正确率、完整性与可控性。

评测必须可重复执行，不要求用户手工修改代码、运行命令或整理结果。每次执行保留输入、Codex 输出、代码差异、自动测试结果和汇总报告，以便定位产品优势与缺陷。

## 2. 评测对象与边界

评测对象包含完整价值链：

1. 用户在样例网页中表达修改需求。
2. 基线组直接将自然语言需求交给 Codex。
3. 实验组使用基于 PatchBrief 输出契约构造的结构化任务书交给 Codex。
4. Codex 在相同初始项目副本中执行修改。
5. 隐藏验收测试和评分器比较两组结果。

首版不把以下事项作为核心评分对象：

- 不依赖真实线上网站或其持续稳定性。
- 不评价不同 AI 模型之间的优劣。
- 不要求真人完成重复操作。
- 不把 PatchBrief 自动修改源码作为能力，因为产品没有这项能力。

首版允许使用确定性的 PatchBrief Brief fixture，而不强制在每轮评测中通过浏览器 UI 手动生成 Brief。另设 PatchBrief 合同测试，验证 fixture 中使用的字段与当前产品输出结构一致。这样可以把“任务书价值评测”和“Bookmarklet UI 回归”分离，避免 UI 波动污染 A/B 结论。

## 3. 目标用户

### 3.1 完全小白

用户只描述看到的问题，不提供组件名、文件名或技术实现。成功意味着 AI 能依据页面目标和结构化上下文完成修改，用户不需要理解或编辑代码。

### 3.2 开发者

用户提供明确的技术边界或实现约束。成功意味着修改准确、范围受控、符合现有工程模式并通过回归测试。

### 3.3 产品或设计人员

用户能表达视觉和交互要求，但通常不掌握源码结构。成功意味着页面视觉层级、状态完整性、响应式和无障碍表现符合验收要求。

## 4. 首版任务集

首版固定 12 个任务，每个任务对应一个独立的小型前端 fixture。fixture 使用原生 HTML、CSS 和 JavaScript，避免框架依赖下载影响可重复性；开发者任务可加入本地 TypeScript 编译或静态约束，但不得要求联网安装依赖。

| ID | 用户 | 任务 | 主要能力 | 关键隐藏要求 |
|---|---|---|---|---|
| N01 | 小白 | 让危险操作按钮更醒目但不误触 | 模糊视觉意图 | 危险语义、focus、移动端不溢出 |
| N02 | 小白 | 提交时防止反复点击 | 状态反馈 | loading、disabled、重复提交保护 |
| N03 | 小白 | 没有搜索结果时给出帮助 | 空状态 | 保留搜索词、清除入口、语义提示 |
| N04 | 小白 | 手机上的导航更好用 | 响应式 | 键盘操作、菜单关闭、桌面端不回归 |
| N05 | 小白 | 表单填错时说清楚 | 错误提示 | 字段关联、焦点、原值保留 |
| D01 | 开发者 | 只修改指定卡片组件的状态逻辑 | 精确范围 | 不改公共 API、不影响兄弟实例 |
| D02 | 开发者 | 修复异步搜索竞态 | 数据流 | 旧请求不得覆盖新结果 |
| D03 | 开发者 | 修复事件监听泄漏 | 生命周期 | 重复挂载无重复监听、正确清理 |
| D04 | 开发者 | 扩展公共按钮 variant | 公共组件 | 向后兼容、复用 token、调用方最小改动 |
| D05 | 开发者 | 支持动态插入的列表项 | 动态 DOM | 事件委托、已有行为不回归 |
| P01 | 产品/设计 | 按参考状态重做统计卡片 | 视觉还原 | 信息层级、长文本、窄屏布局 |
| P02 | 产品/设计 | 补全交互控件全部状态 | 状态系统 | hover、focus、disabled、loading、对比度 |

每个任务必须提供：

- `task.json`：用户类型、自然语言需求、Brief、超时和评分权重。
- `starter/`：不可变初始项目。
- `tests/`：对模型隐藏的 Node 测试。
- `expected-scope.json`：允许修改的路径或范围。
- 可选参考图及视觉断言。

## 5. A/B 实验协议

每个任务生成两次相互隔离的执行：

### A 组：自然语言基线

Codex 只收到用户原始需求、项目运行方法和“完成并验证修改”的通用指令。不得包含 PatchBrief 提取出的 Selector、Locator、区域、视觉摘要、局部 HTML、相关代码或结构化约束。

### B 组：PatchBrief

Codex 收到同一原始需求及完整 Frontend Change Brief。Brief 至少包含适用字段：

- 修改目标；
- 页面上下文；
- 选中目标；
- Selector；
- 语义 Locator；
- 区域和尺寸；
- 局部 HTML 摘要；
- 视觉摘要；
- 相关代码；
- 修改约束；
- 预期结果；
- 安全执行要求。

### 控制变量

- 两组从相同 starter 内容开始。
- 使用相同模型、推理强度、沙箱权限和超时。
- 使用全新 Codex 会话，不共享另一组结果。
- 任务运行顺序随机化，但报告保留配对关系。
- Codex 无法读取隐藏测试和评分配置；运行目录只包含 starter 和公开说明。
- runner 不允许模型修改评测仓库本身。
- 首轮每个条件执行一次；异常分差、执行错误或硬失败任务自动加入复跑清单。

## 6. 执行架构

评测包位于独立仓库，不修改 PatchBrief 产品源码。核心模块：

1. **Manifest loader**：读取并校验 12 个任务定义。
2. **Workspace preparer**：为每次运行创建独立临时目录并复制 starter。
3. **Prompt builder**：生成严格区分的 A/B Prompt。
4. **Codex runner**：通过本机 `codex exec` 非交互执行，记录标准输出、标准错误、退出码、耗时和会话元数据。
5. **Deterministic grader**：运行隐藏功能测试、构建检查、DOM/源文件断言和范围检查。
6. **Quality grader**：根据静态规则衡量重复代码、调试残留、API 兼容和可访问性。
7. **Report generator**：输出 JSON、Markdown 和单文件 HTML 报告。

执行命令：

```bash
npm run eval:validate
npm run eval:smoke
npm run eval
npm run eval:report
```

`eval:smoke` 只运行 N01 和 D01 的 A/B，共 4 次 Codex 执行。`eval` 运行全部 12 个任务的 A/B，共 24 次。`eval:report` 不调用 Codex，只根据已有原始结果重建报告。

## 7. 数据流与产物

每次运行生成唯一 run ID：

```text
任务定义
  -> A/B prompt
  -> 隔离工作目录
  -> codex exec
  -> diff + execution.json
  -> hidden tests + static graders
  -> score.json
  -> aggregate.json / report.md / report.html
```

结果目录不提交 Git：

```text
results/<run-id>/
  manifest.json
  executions/<task-id>/<arm>/
    prompt.md
    codex.stdout.txt
    codex.stderr.txt
    diff.patch
    execution.json
    test-results.json
    score.json
  aggregate.json
  report.md
  report.html
```

报告必须能从磁盘直接打开，不依赖服务端或外部 CDN。

## 8. 评分体系

每个任务 100 分：

| 维度 | 分值 | 评测方式 |
|---|---:|---|
| 隐藏功能验收 | 35 | Node 行为测试、DOM 断言、状态测试 |
| 用户要求覆盖 | 20 | 任务专属可验证检查点 |
| 回归和构建安全 | 15 | 基线测试、语法检查、控制台错误检查 |
| 修改范围控制 | 10 | 文件白名单、diff 统计、禁止路径 |
| 代码质量 | 10 | 静态规则和任务专属架构约束 |
| 视觉、响应式、无障碍 | 10 | CSS/DOM 断言、视口检查、axe 可用时增强 |

任务结果分为：

- `complete`：总分不低于 85，所有必要检查点通过，且无硬失败。
- `partial`：总分 50–84，或必要检查点存在遗漏。
- `failed`：总分低于 50，或发生硬失败。
- `execution_error`：Codex 未完成执行、超时或环境错误；不应混入产品失败率，报告单列。

### 硬失败条件

- 项目无法构建或启动。
- 核心原有功能损坏。
- 删除、篡改或读取隐藏测试。
- 泄漏 fixture 中设置的敏感值。
- 通过屏蔽异常、删除断言或放宽验证来伪造成功。
- 未经需求大范围重写项目。

## 9. 核心指标

北极星指标为 **配对有效任务完成率提升**：

```text
PatchBrief 完全成功率 - 自然语言完全成功率
```

同时报告：

- A/B 平均分和中位数差；
- 按小白、开发者、产品设计分组的成功率差；
- PatchBrief 胜、平、负的任务数量；
- 严重回归率；
- 越界修改率；
- 执行错误率；
- P50/P90 完成时间；
- Codex 调用次数；
- 各 Brief 字段在胜负案例中的出现情况；
- 失败类型分布。

首轮不预设“PatchBrief 一定有效”。报告必须允许出现负提升，并指出额外上下文造成噪声的任务。

## 10. PatchBrief 自身合同测试

除下游 A/B 外，评测包还必须检查当前 PatchBrief 项目：

- 产品仓库能够定位；
- `dist/patchbrief.runtime.js` 存在；
- README 声明与评测假设一致；
- 示例 Brief 与任务 fixture 的字段契约一致；
- PatchBrief 原项目已有测试命令可被只读调用；
- 任务书不得包含表单真实值、密码、token、cookie、authorization、secret、session、CSRF、API key 或高熵敏感串。

这些合同测试与 A/B 得分分开展示，避免把产品运行时回归和下游效果混为一个分数。

## 11. 错误处理

- 找不到 PatchBrief 项目时，验证命令失败并输出可配置路径。
- 找不到 Codex CLI 或未登录时，执行命令在创建工作目录前失败。
- 单个任务超时只标记该执行为 `execution_error`，其余任务继续。
- 中断后再次执行默认跳过已经完成且输入哈希一致的任务。
- Prompt、模型、任务或 starter 改变后，输入哈希变化，旧缓存不得复用。
- 报告生成器必须容忍部分完成的 run，并明确已完成和缺失的实验臂。

## 12. 公平性与防污染

- 隐藏测试存放在 runner 侧，不复制到 Codex 工作目录。
- A/B Prompt 除 PatchBrief 信息差异外保持同一执行模板。
- 评分器不调用被测 Codex 会话进行自评。
- 自动评分规则在运行前固定，并记录版本哈希。
- 报告展示原始检查点结果，不能只展示一个不透明总分。
- 视觉主观项首版仅占低权重；不能稳定自动化的项目标记为 `review_required`，不伪装成客观分数。

## 13. 验收标准

评测包完成需满足：

1. 12 个任务均通过 schema 校验。
2. smoke 模式能够自动完成 4 次隔离执行并生成三种报告。
3. 完整模式能独立运行 24 次执行，单任务失败不终止全局。
4. 报告能重建且结果一致。
5. 至少一个故意错误实现能被每个任务的隐藏测试拒绝。
6. 自然语言组 Prompt 不含 PatchBrief 独有字段。
7. PatchBrief 组 Prompt 符合当前 Brief 契约。
8. 工作目录、缓存和结果路径不会污染 PatchBrief 产品仓库。
9. README 提供由 Codex 执行的操作说明，用户不需要承担评测操作。

## 14. 首轮评测决策规则

首次基线结果不直接决定产品成败，而用于校准测试集：

- 如果两组均接近满分，任务缺乏区分度，应提高歧义或上下文定位难度。
- 如果两组均大量失败，应检查 fixture、Prompt 或隐藏测试是否不合理。
- 如果 PatchBrief 在小白任务显著提升而开发者任务持平，这是可接受且有产品意义的结果。
- 如果 PatchBrief 平均分提高但完成时间和越界修改明显恶化，报告应判定为有条件收益。
- 如果 PatchBrief 组表现下降，应逐题识别是字段噪声、错误定位还是任务书过长，不调整评分来制造正向结论。
