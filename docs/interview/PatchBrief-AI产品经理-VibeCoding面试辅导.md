# PatchBrief：AI 产品经理 Vibe Coding 面试辅导

> 用途：面试前复习、项目介绍、连续追问演练。  
> 事实边界：答案只使用当前仓库中已经完成的功能和验证结果；未完成的用户研究、数据和功能会明确标注，不包装成真实成绩。

## 一、面试定位

### 1. 一句话项目介绍

PatchBrief 是一个纯浏览器端的视觉修改任务书工具。用户在网页上选中需要修改的位置，补充修改要求、相关代码和约束，即可生成结构化的 Frontend Change Brief，交给 AI 编码助手执行。

### 2. 这个项目能证明什么

它最适合证明以下能力：

- 能从模糊痛点切出可验证的 MVP，而不是停留在 PRD 或静态原型。
- 能借助 AI 编程完成需求拆解、工程实现、调试、测试、构建和部署闭环。
- 能理解浏览器安全边界，并在产品方案里设计隐私、降级和错误处理。
- 能对 AI 生成代码做验收，而不是把“代码生成成功”当作“产品完成”。
- 能把产品要求转译成明确的技术约束和自动化验收标准。

这个项目不能直接证明：

- RAG、向量检索、模型微调或 Agent Tool Calling 的生产经验。
- 已获得真实用户增长、留存或商业收入。
- 已完成大规模用户研究或 A/B 实验。
- 已经支持所有网页和浏览器内部页面。

## 二、可直接使用的项目讲述

### 90 秒标准版

我做了一个叫 PatchBrief 的 Vibe Coding 项目，目标用户是使用 AI 编码助手的个人开发者。真实痛点不是 AI 不会写代码，而是用户很难把“页面这里需要改一下”转化成包含页面位置、元素语义、相关代码和约束的清晰任务。

我把 MVP 定义为一个不需要安装扩展和后端的 Bookmarklet：用户把按钮拖到书签栏，在普通网页点击后进入检查模式，选择元素、填写修改目标和约束，生成结构化 Frontend Change Brief。方案上我选择 TypeScript、原生 DOM API 和 Shadow DOM，所有运行时代码打包进书签；这样安装门槛低、网页数据不上传，也避免目标网站的 CSS 污染工具面板。

我不是只让 AI 生成界面，而是先把需求拆成 Selector 稳定性、语义定位、HTML 脱敏、动态 DOM、重复启动和完整清理等可验收问题，再用单元测试和 Playwright 浏览器测试验证。最终项目可以构建为 GitHub Pages 安装页和单文件书签运行时，构建脚本还会检查语法、payload 重组、相对路径、源码路径泄漏和体积预算。

目前工程闭环已经跑通，但真实用户验证仍不足，所以我不会把它说成已经验证商业价值。下一步我会用开发者任务测试，比较“截图加口述”和“PatchBrief 任务书”在需求澄清次数、首次修改命中率和任务准备时长上的差异。

### 30 秒精简版

PatchBrief 是我用 Vibe Coding 完成的纯前端开发者工具。它让用户直接在网页上选择修改位置，并把 DOM 定位、语义、视觉信息、代码和约束整理成可交给 AI 编码助手的结构化任务书。我负责从问题定义、MVP 取舍到实现验收，重点处理了 Shadow DOM 隔离、Selector 稳定性、敏感信息清理、动态页面和构建部署。当前能证明工程可用性，但用户价值指标还需要真实测试补齐。

## 三、项目讲述题与连续追问

### Q1：为什么要做 PatchBrief？

**考察点：** 是否从用户问题出发，而不是从技术或功能出发。

**参考答案：**

使用 AI 编码助手修改前端时，用户通常会说“把这个按钮改红”“这里间距大一点”，但 AI 缺少准确的页面位置、组件语义、相关代码和约束。截图能表达视觉，却不能稳定定位 DOM；CSS Selector 能定位，却不能表达修改意图。PatchBrief 解决的是“视觉意图到工程任务”的信息损耗，而不是再做一个元素选择器。

**追问：已经有截图和 DevTools，为什么还需要它？**

截图、DevTools 和 PatchBrief 解决的问题不同。截图偏视觉，DevTools 偏开发调试，PatchBrief 偏任务交接：把位置、语义、视觉状态、用户要求和工程约束合成一份统一输入。它的价值假设是减少反复澄清，而不是替代 DevTools。

**追问：这个痛点经过验证吗？**

当前主要来自个人使用场景和工作流观察，还没有形成足够的外部访谈样本，因此我把它称为“待验证假设”，不称为已验证需求。下一步会找使用 Cursor、Codex 或 Claude Code 的开发者完成同一修改任务，记录准备时间、追问次数和首次命中率。

### Q2：你的目标用户是谁？为什么不是所有人？

**参考答案：**

首要用户是能打开本地开发页面、会使用 AI 编码助手，但不希望每次都手工描述 DOM 上下文的个人开发者。没有技术背景的普通用户也可能使用，但他们通常无法补充相关代码和判断修改约束，所以不是第一阶段核心用户。先聚焦个人开发者可以降低权限、团队协作和企业治理复杂度。

### Q3：你在项目中具体负责什么？

**参考答案：**

我负责完整产品闭环：定义用户问题和边界、拆解需求、确定 Bookmarklet 架构、设计安装和使用流程、给 AI 编码代理提供约束、检查实现、根据失败结果继续修正，并建立测试、构建和部署验收。编码大量由 AI 辅助完成，但需求判断、范围取舍和最终验收责任在我。

**危险回答：**“这个项目都是我独立写的。”如果实际使用了 AI，这种说法既不准确，也失去了展示 AI 协作能力的机会。

### Q4：为什么选择 Bookmarklet，而不是浏览器扩展？

**参考答案：**

MVP 的核心假设是用户是否愿意通过“网页选点”生成任务书，而不是验证扩展商店分发和权限体系。Bookmarklet 无需商店审核、无需持续后台权限，也能在 localhost 使用，最适合快速验证。代价是不能运行在浏览器内部页面、跨域 iframe 能力有限、脚本长度和浏览器兼容性受约束。若后续数据证明用户需要团队分发、更稳定权限或深层页面集成，再评估扩展版本。

### Q5：为什么不做后端？

**参考答案：**

核心流程只需要读取当前 DOM 并生成文本，本地即可完成。引入后端会增加账号、数据上传、隐私、运维和成本，但不直接增强核心价值。因此 MVP 选择无后端，让数据不离开页面。代价是不能跨设备同步、不能做云端历史和服务端分析，这些不是第一阶段必须能力。

### Q6：项目最大的产品取舍是什么？

**参考答案：**

最大的取舍是“安装轻量”和“能力完整”之间的权衡。我选择 Bookmarklet，优先降低安装门槛和隐私风险，并接受内部页面、跨域 iframe 和截图权限方面的限制。另一个取舍是不用 React/Vue 和大型截图依赖，控制运行时体积和页面侵入，但增加了原生状态管理和界面维护成本。

### Q7：MVP 为什么包含这么多工程约束？是不是过度设计？

**参考答案：**

我把功能分成核心价值和可信使用两类。选择元素、填写要求、生成任务书是核心价值；样式隔离、清理、隐私和重复启动是 Bookmarklet 能否实际使用的最低可信门槛。没有这些，Demo 虽然能展示，但可能破坏目标网页或泄露输入值。截图、完整设置等能力则应当后置。回看当前版本，范围仍可进一步收紧，尤其截图模块尚未接入，不应把它计入已交付功能。

### Q8：如果重做一次，你会改变什么？

**参考答案：**

我会把真实任务验证提前到工程实现之前：先用可点击原型或简化脚本测试三到五名开发者，观察他们是否理解安装方式、会选哪个元素、生成内容是否真的减少 AI 追问。其次，我会把验收清单分成“本版本必须”和“后续版本”，避免功能文件已存在但入口未接通的情况。最后，我会为关键产品指标预留匿名、用户主动导出的本地统计，而不是默认上传埋点。

### Q9：这个项目现在完成了吗？

**参考答案：**

工程 MVP 已形成闭环：安装页、书签注入、悬停、选择、多选、表单、拖框截图、任务书生成、复制下载、测试构建和 Pages 工作流均有实现。但不能说产品验证已经完成。方向键层级导航、草稿历史、完整设置和完整中英文面板尚未完成；真实用户价值和使用指标也没有验证。

### Q10：最大的困难是什么？

**参考答案：**

困难不是生成某个页面，而是在任意第三方网页中运行且尽量不破坏原页面。我把问题拆成四类：事件拦截、样式隔离、稳定定位和清理恢复。使用 Shadow DOM 隔离面板 CSS；Overlay 使用固定定位和 pointer-events none；Selector 每个候选都验证唯一性并过滤哈希和工具类；关闭时移除监听器、Overlay、宿主和全局控制对象。这个拆分让问题可以分别测试，而不是靠手工感觉。

## 四、产品判断题与答案

### Q11：如何判断它是真需求？

**参考答案：**

我会验证四件事：用户是否高频使用 AI 修改前端；表达修改意图是否经常产生澄清；澄清是否造成明显时间成本或错误修改；结构化任务书是否比截图加口述更有效。证据应包含访谈、任务观察和对照数据。只有“用户觉得很酷”不能证明需求成立。

### Q12：核心成功指标是什么？

**参考答案：**

北极星指标可以定义为“使用 PatchBrief 后，一次提交即可被 AI 正确理解并完成的前端修改任务比例”。过程指标包括任务书生成完成率、从启动到生成的时长、平均选中目标数和复制率；结果指标包括 AI 首次修改命中率、后续澄清轮数和人工返工时间；护栏指标包括敏感信息泄露事件、页面被工具破坏的比例和启动失败率。

### Q13：怎么证明价值来自 PatchBrief，而不是模型变强了？

**参考答案：**

做同模型、同代码库、同修改任务的对照实验。A 组使用截图加自然语言，B 组使用 PatchBrief 任务书，固定模型版本和提示规则，对比首次命中率、澄清轮数、总耗时和无关文件修改数。样本按简单样式、交互修改和多元素联动分层，避免只测最容易的任务。

### Q14：什么证据会让你停止项目？

**参考答案：**

如果目标开发者很少遇到描述困难，或者生成任务书的操作成本高于节省的沟通成本；又或者现代编码助手已能稳定读取浏览器和代码上下文，使独立任务书没有增量价值，我会停止或转向。停止条件应提前定义，例如对照实验中首次命中率和总耗时都没有改善，且访谈显示安装方式阻力高。

### Q15：如何排需求优先级？

**参考答案：**

先围绕“能否完成一次任务交接”排序：启动与选择、任务描述、结构化输出、复制是 P0；稳定 Selector、语义和脱敏属于可信使用的 P0；多选、撤销、动态 DOM 是高频效率 P1；截图、历史、团队模板属于 P2。排序依据是用户任务必要性、风险、验证价值和实现成本，而不是功能数量。

### Q16：为什么要输出 HTML？会不会有风险？

**参考答案：**

局部 HTML 能帮助 AI 判断层级和属性，但不是所有任务都需要，所以应是可控能力。当前清理逻辑会移除脚本、样式、事件属性、输入值、敏感字段名和高熵字符串，密码框只保留类型。产品上还应允许用户关闭 HTML，并在预览中检查后再复制。风险不能靠一句“本地运行”消除，仍要做最小采集和显式控制。

### Q17：如果用户不会选元素怎么办？

**参考答案：**

这属于关键可用性风险。可以通过悬停语义提示、单击后卡片反馈、父子层级导航和“选择过大”的提示降低门槛。验证时要观察用户会选 body、容器还是按钮，并记录纠正次数。当前项目已经支持悬停、单选和多选，但完整方向键层级导航尚未实现，应列为下一轮高优先级。

### Q18：为什么不直接让 AI 读取网页？

**参考答案：**

如果 AI 编码工具已经安全地连接浏览器和代码仓库，直接读取上下文可能更流畅。但不同工具的浏览器连接能力、权限和稳定性并不一致。PatchBrief 的定位是可移植、模型无关的结构化交接层。长期是否独立存在，要由集成趋势和用户数据决定，而不是预设它一定有价值。

## 五、Vibe Coding 与技术深挖

### Q19：你如何用 AI 编程完成这个项目？

**参考答案：**

我先给出产品定义、边界、数据模型、交互和验收标准，再让 AI 按模块实现。我要求先检查工作区、建立最小注入闭环，再依次完成选择、上下文、面板、输出、构建和测试。每次出现问题，不是重新生成整个项目，而是根据测试或浏览器现象缩小范围，修改对应模块并回归验证。

### Q20：如何避免 AI 一次生成大量不可控代码？

**参考答案：**

把需求切成可独立验收的垂直切片，每片写清输入、输出、边界和测试。例如 Selector 模块只负责候选优先级、稳定性过滤和唯一性验证；Sanitizer 只负责敏感内容清理；Prompt 模块只负责字段省略和结构化输出。这样出错时可以定位到模块，也能通过测试阻止回归。

### Q21：哪部分代码你必须能解释？

**参考答案：**

至少要解释完整数据流和高风险模块：书签如何注入、事件如何捕获、元素如何解析、Selector 如何生成、上下文如何清理、Draft 如何变成 Markdown、复制下载如何执行、关闭时如何恢复页面。即使不能逐行默写，也必须说明每个模块为什么存在、输入输出是什么、失败会发生什么。

### Q22：请解释完整数据流。

**参考答案：**

用户点击书签后，IIFE 检查全局控制对象，避免重复注入；随后创建 Shadow DOM 面板和 Overlay，注册 pointer、click、scroll、resize、keydown 监听。点击目标后读取元素的可访问名称、Selector、Locator、区域、视觉和脱敏 HTML，保存在内存 SelectionRecord 中。用户填写表单后组装 BriefDraft，再生成 Markdown 或 JSON，最后复制或下载。关闭时移除监听器、Overlay、宿主和全局对象。

### Q23：为什么使用 Shadow DOM？

**参考答案：**

工具运行在未知网页中，宿主页面可能有全局 button、textarea、box-sizing 或字体样式。Shadow DOM 为面板建立样式边界，降低宿主 CSS 污染。Overlay 需要覆盖页面，所以放在页面顶层，但使用严格命名空间和 pointer-events none，避免阻挡交互。

### Q24：Selector 怎么保证稳定？

**参考答案：**

候选优先级从 data-testid、data-test、data-cy、data-qa，到稳定 ID、aria-label、name、title、语义 class，再到祖先路径和 nth-of-type。每个候选必须通过 querySelectorAll 结果唯一的验证。同时过滤 UUID、长哈希、React 自动 ID、CSS-in-JS、CSS Modules 和 Tailwind 工具类。无法形成可靠且不过长的 Selector 时宁可不输出，使用语义 Locator 补充。

### Q25：动态 DOM 怎么处理？

**参考答案：**

工具不在初始化时扫描并标记整棵 DOM，而是在用户交互时即时解析目标，所以之后新增的元素也可选。选择记录保留 Element 引用；如果元素仍连接页面，滚动和缩放时更新 Overlay；如果被删除，卡片标记目标失效但不让整个面板崩溃，用户仍可删除该记录。

### Q26：如何处理性能？

**参考答案：**

pointermove 只记录最后目标，并通过 requestAnimationFrame 每帧处理一次，避免每个鼠标事件都读取布局。工具不做全量 DOM 扫描。滚动和窗口变化只重定位已选择元素。后续还应在高频重绘页面中增加更严格的滚动节流和性能采样。

### Q27：如何保证不破坏原网页？

**参考答案：**

面板使用 Shadow DOM，Overlay 不参与页面布局且不接收指针事件；只在检查模式下拦截点击；输入框聚焦时不劫持快捷键；关闭时移除所有监听器、Overlay、宿主和 window 控制对象。E2E 测试验证关闭后宿主和工具节点被清理。

### Q28：为什么不用 React 或 Vue？

**参考答案：**

Bookmarklet 对体积、启动时间和宿主环境兼容性敏感，面板状态规模有限，原生 DOM 足以完成 MVP。省掉框架可以降低运行时体积和依赖风险。代价是渲染逻辑更手工，复杂状态扩张后维护成本会上升；如果未来形成复杂工作台或扩展版，再评估组件框架。

### Q29：如何判断 AI 生成代码质量？

**参考答案：**

不是看代码能否启动，而是分层验收：类型检查验证接口一致性；单元测试验证 Selector、脱敏、上下文和任务书；Playwright 验证真实浏览器中的注入、选择、动态 DOM 和清理；构建验证检查 IIFE 语法、payload 可重组、Pages 路径、源码泄漏和体积预算。最后还要人工检查交互和浏览器限制。

### Q30：你遇到过什么实际错误，如何定位？

**参考答案：**

一个例子是宽屏安装页仍固定在 1160px，导致超宽浏览器中内容缩在中央。我先增加一个 2880px 视口的浏览器测试，确认主体宽度只有 1160px并让测试失败；然后只调整安装页的桌面布局上限、首屏比例和文字行宽，重新构建并运行完整测试。另一个环境问题是系统 PATH 没有 Node/npm，我没有跳过验证，而是定位应用内置 Node 运行时继续执行测试。

### Q31：为什么需要构建 payload？

**参考答案：**

用户不能被要求复制长段 JavaScript。构建流程把 TypeScript 打包为单个 IIFE，加上 javascript: 前缀，再 Base64 编码并按需切片。安装页从自身域名加载 manifest 和 payload，组装后设置到可拖动按钮。验证脚本会反向组装并比较原文，防止发布出损坏书签。

### Q32：项目如何部署？

**参考答案：**

构建输出是纯静态 dist，可部署到 GitHub Pages。所有路径使用相对路径以兼容仓库子目录；工作流在 main 更新后安装依赖、检查、构建、上传 Pages artifact 并部署。运行时书签不依赖 CDN 或第三方 API。

## 六、安全、隐私与异常处理

### Q33：项目为什么强调隐私？

**参考答案：**

用户可能在内部系统或带敏感数据的页面上选元素，还会粘贴源码。如果工具默认上传 DOM、代码或截图，会形成高风险。PatchBrief 选择全部本地处理，不读取 Cookie、网络请求或本地源码，草稿默认不持久化，并在输出 HTML 前做敏感信息清理。

### Q34：本地运行就绝对安全吗？

**参考答案：**

不是。本地运行降低了网络上传风险，但仍可能把敏感内容复制进任务书，再由用户粘贴给外部 AI。因此还需要最小采集、脱敏、预览确认、可关闭 HTML 和清晰提示。当前已经有脱敏和预览，设置项与更细粒度控制仍需完善。

### Q35：截图为什么不能静默完成？

**参考答案：**

浏览器 Screen Capture API 必须由用户主动授权并选择共享目标，这是安全边界。PatchBrief 已把截图接入面板：用户选择当前标签页后拖出矩形，可预览、复制或下载 PNG；取消授权与截图失败都不会阻塞任务书生成。它只能截当前可见视口，不能静默截图或绕过浏览器权限。

### Q36：跨域 iframe 怎么办？

**参考答案：**

同源 iframe 可以在满足权限和实现支持时访问内部 DOM；跨域 iframe 受同源策略限制，只能把 iframe 元素本身作为目标，不能绕过浏览器安全策略。产品上要明确提示边界，而不是伪装选择成功。

### Q37：如果 Clipboard API 失败怎么办？

**参考答案：**

先使用 navigator.clipboard.writeText，失败时可降级到隐藏 textarea 和 execCommand copy；仍失败则提示用户手动选择预览文本。当前代码有复制降级模块，但复制成功或失败反馈还应继续加强，这是可用性而不是纯技术细节。

### Q38：为什么暴露 window.__PATCHBRIEF__？

**参考答案：**

只暴露一个最小控制对象，用于重复启动时聚焦已有实例，以及 open、pause、resume、destroy 和版本控制。其他状态保留在 IIFE 闭包中，减少对宿主页面全局空间的污染。

## 七、评测、指标和用户验证

### Q39：你会怎么设计第一轮用户测试？

**参考答案：**

招募三到五名经常使用 AI 编码助手的开发者，每人完成三类任务：单元素样式、多元素布局、带交互约束的修改。先使用原方法，再使用 PatchBrief；记录任务描述准备时间、AI 澄清轮数、首次命中率、无关改动和主观负担。任务后访谈他们在哪一步犹豫、哪些信息没有价值、是否愿意再次使用。

### Q40：样本很少，结论可信吗？

**参考答案：**

小样本适合发现可用性问题和验证方向，不适合宣称统计显著。第一轮目标是识别阻塞点和形成假设；之后扩大任务和用户样本，并保持同模型、同代码库和同任务的对照。报告中区分观察、推断和结论，避免把个别反馈当市场证明。

### Q41：上线后先看什么数据？

**参考答案：**

先看漏斗：安装页访问、书签准备成功、拖入书签栏、成功启动、至少选择一个元素、生成任务书、复制或下载。然后看结果：任务书是否被实际使用、AI 首次修改命中率和节省的澄清时间。由于产品强调隐私，默认不应暗中上传行为数据，可通过用户主动导出匿名诊断或自愿参与测试收集。

### Q42：如果生成率高但复用率低，怎么分析？

**参考答案：**

先区分新鲜感使用和真实价值。检查任务书是否太长、选择步骤是否比直接描述更慢、AI 是否已经能自动获得上下文，以及安装方式是否难以形成习惯。结合复访和任务录像做漏斗分层，不能只靠生成次数判断成功。

### Q43：如果任务书更完整，但 AI 修改结果没有提升怎么办？

**参考答案：**

按链路拆解：定位信息是否能映射到代码组件；任务目标是否明确；相关代码是否足够；约束是否互相冲突；AI 工具是否真正使用了这些字段。然后做字段消融实验，比较只给语义、加入 Selector、加入代码、加入约束后的变化。如果结构化信息没有增益，就要简化产品或改变定位。

## 八、岗位层级追问

### Q44：如果应聘 1–3 年 AI 产品经理，怎么讲？

**参考答案：**

重点讲独立执行闭环：如何把需求拆成 MVP，如何让 AI 生成可控代码，如何读错误、补测试、完成构建和可访问 Demo；同时诚实说明用户验证下一步。少讲宏大平台战略，多讲自己具体完成了什么、怎么验收。

### Q45：如果应聘 3–5 年岗位，怎么讲？

**参考答案：**

重点讲取舍和 ownership：为什么选择 Bookmarklet 而不是扩展，为什么不做后端，如何在安装门槛、能力、隐私和维护成本间决策，怎样定义停止条件、指标和路线图。但不能只把初级执行换成高级词汇；没有真实 ROI 和跨团队资源协调证据时，要明确这是个人项目的局限。

### Q46：应聘 AI 工具或开发者平台 PM，重点讲什么？

**参考答案：**

讲开发者任务链路和可解释性：从视觉意图到 DOM 上下文，再到结构化任务；讲 Selector、语义 Locator、代码约束和模型无关输出；讲兼容性、体积、部署和失败降级。还要补开发者访谈和竞品工作流对照，否则容易变成纯工程作品。

### Q47：应聘 Agent/RAG 岗位，能把这个项目说成 Agent 项目吗？

**参考答案：**

不能。PatchBrief 为 AI 编码助手准备结构化输入，但自身没有模型决策、工具调用、记忆、任务规划或 RAG 检索链路。可以说它体现了“人机协作中的上下文工程和任务结构化”，作为相邻能力证据；Agent/RAG 岗位仍需另一个能解释架构、评测和 Badcase 的真实项目。

### Q48：为什么你适合 AI 产品经理？

**参考答案：**

我的优势不是只会写文档，也不是把自己包装成专业工程师，而是能把产品判断快速变成真实、可测试的产品证据。PatchBrief 展示了我能定义问题、做范围取舍、理解技术边界、组织 AI 编程、建立验收和诚实识别未验证部分。下一步我要补强的是用户研究、指标和业务结果，让工程闭环继续延伸到产品闭环。

## 九、压力追问与短答案

### Q49：这不就是一个 CSS Selector 复制器吗？

不是。Selector 只是一个字段。核心产物还包含页面上下文、元素语义、区域、视觉摘要、元素级说明、全局目标、相关代码、约束、预期结果和执行要求；目标是完成工程任务交接。

### Q50：GitHub 上可能已经有类似项目，你的创新在哪里？

我不会把“全球首创”当卖点。差异假设在于任务书工作流、隐私优先和模型无关交接。是否形成真实优势要通过竞品任务对照和用户选择验证，而不是靠功能描述证明。

### Q51：AI 写了代码，那你的价值是什么？

AI 提升了实现速度，但它不会替我确定目标用户、范围、风险、验收标准和停止条件。我的价值体现在把模糊意图变成可验证系统，并对最终结果负责。与此同时，我必须能解释关键数据流和风险代码，否则就不能声称拥有项目。

### Q52：没有后端、没有模型，算 AI 产品吗？

它是 AI 工作流工具，不是模型产品。它服务于 AI 编码过程中的上下文与任务交接，价值取决于是否提升 AI 修改任务的成功率。面试时我会准确称为“面向 AI 编码助手的开发者工具”，不会夸大为大模型平台。

### Q53：为什么现在没有用户数据？

当前先完成了工程可行性验证，但用户验证启动得偏晚，这是项目复盘中的不足。正确做法不是编造数据，而是给出明确测试方案、样本、指标和停止条件，并尽快补齐真实记录。

### Q54：项目代码看起来很紧凑，可维护性好吗？

当前运行时为了控制书签体积，核心入口较紧凑，但模块已经按 Selector、Sanitizer、Context、Prompt、Clipboard 等职责拆分。继续迭代前应把入口中的状态、渲染和事件进一步拆开，同时保持构建体积和回归测试。不能用“体积小”掩盖可维护性问题。

### Q55：为什么测试数量不多？

现有测试覆盖了关键算法和核心浏览器闭环，但与最初完整需求相比仍不够，尤其是快捷键导航、复制失败反馈、截图入口、iframe、全局 CSS 污染和失效元素卡片需要更完整 E2E。我的原则是如实描述当前覆盖，不用“有自动化测试”替代覆盖率分析。

### Q56：如果资源减半，你保留什么？

保留安装、选择、填写核心要求、生成和复制五步，以及 Selector、脱敏和完整清理三项可信底座。先砍截图、复杂设置、历史、面板位置和非核心浏览器优化，因为它们不是验证核心价值的必要条件。

### Q57：如果浏览器厂商限制 Bookmarklet 怎么办？

先评估影响范围和目标用户占比。短期提供清晰兼容说明；中期可验证浏览器扩展或开发服务器脚本版本；长期保持 Brief 数据模型和生成逻辑独立，让入口形态可以替换。架构不应把产品价值锁死在 Bookmarklet 上。

### Q58：这个项目的商业模式是什么？

当前阶段不应先讲收费。先验证个人开发者是否持续使用，以及任务成功率是否提升。若价值成立，可能的方向包括团队模板、规范治理、任务历史、协作和 IDE/代码仓库集成，但这些涉及后端和组织数据，必须重新评估隐私、权限和成本。

## 十一、面试危险信号

以下表达尽量避免：

- “我让 AI 一次就把项目写完了。”
- “这个产品支持所有网页。”
- “数据都在本地，所以绝对安全。”
- “我们已经提升了开发效率。”——目前没有真实对照数据。
- “这是一个 Agent 项目。”——当前没有 Agent 链路。
- “截图不需要授权、可以自动截整页。”——实际功能必须由用户选择共享标签页，且只支持当前视口拖框。
- “完整支持中英文。”——安装页有切换，面板文案仍有硬编码。
- “所有测试都覆盖了。”——关键闭环有测试，但完整需求仍有缺口。
- “我不会代码，所以代码细节都是 AI 的。”
- “整个项目都是我手写的。”——与真实 AI 协作过程不符。

## 十二、面试前证据清单

建议面试时准备以下材料：

- GitHub 仓库或本地源码。
- 可打开的 GitHub Pages 或本地安装页。
- 30–60 秒完整演示视频：安装、选择、填写、生成、复制。
- 架构图：安装构建链路和运行时数据流。
- 一页需求—实现—测试映射。
- 一次真实错误的复现、定位和修复记录。
- 当前测试结果截图或 CI 记录。
- 三到五名目标用户的任务测试记录。
- 一页项目复盘：做对了什么、做错了什么、下一步验证什么。

## 十三、推荐补证顺序

1. **先做真实用户任务测试。** 这是从“工程作品”升级为“产品项目”的关键证据。
2. **补齐产品承诺与实际功能。** 优先完成方向键导航、复制反馈和失效元素体验；截图若不接入，就从对外功能清单移除。
3. **形成可展示证据包。** 部署地址、演示视频、指标表、迭代日志和复盘文档一起准备。

## 十四、最终记忆口诀

面试讲 PatchBrief 时始终按这条线回答：

> 真实问题 → MVP 取舍 → 我的判断 → AI 协作方式 → 技术边界 → 测试证据 → 用户指标 → 诚实复盘

如果被追问到不会的技术细节，可以回答：
